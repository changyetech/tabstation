# 重复标签页豁免展示条数折叠

- 日期：2026-08-17
- 状态：已实现
- 修订：[2026-08-16-manager-redesign.md](2026-08-16-manager-redesign.md) §5.2（展示条数折叠）、§5.4（去重）

## 1. 背景与问题

`visibleTabs` 折叠（§5.2）对区块内的 tab 行**无差别**截断到前 N 条。重复标记（`dup-badge`）与 hover 同组高亮（`previewByTabId`）只作用于已渲染的行，于是产生两个缺陷：

- **A. 隐藏的重复不可见** —— 落在折叠区里的重复行连徽标都不渲染，用户无从知道该区块存在重复，「发现重复」这一功能在折叠态下静默失效。
- **B. 同组高亮打在不可见节点上** —— hover 一个「×3」的行时，同组另外两个成员可能位于其他区块的折叠区，高亮无视觉反馈，读起来像故障。

§5.4 原裁决「折叠中的组员**不强制展开**」正是缺陷 B 的来源，本 spec 推翻该裁决。

不属于本 spec 的问题：一键去重预览（`dedupePreview`）已绕过折叠、只渲染重复组成员，行为正确，不改。

## 2. 决策

**重复组成员豁免展示条数折叠。**

理由是语义一致性而非实现便利：折叠的目的是压缩噪音，而重复行恰恰不是噪音——它是用户的行动目标。让「待清理项」被「怕你看太多」的机制藏起来，功能自相矛盾。

被否的替代方案：

| 方案 | 解 A | 解 B | 否决理由 |
| --- | --- | --- | --- |
| more 行追加「其中 N 个重复」计数 | ✅ | ❌ | 只补救知情权，用户仍需多点一步才能动手 |
| hover 同组时临时展开相关区块 | ❌ | ✅ | hover 引发列表高度跳动，hover 目标本身移位，手感差 |
| 区块头加「重复 N」chip + 点击过滤 | ✅ | ❌ | 新增交互面，与已有的一键去重预览职责重叠 |

## 3. 规则

折叠态（未展开）下区块展示的行 = **前 `visibleTabs` 条 ∪ 全部重复组成员**，保持原顺序（不把重复行提前）。

- `hiddenCount` = 总行数 − 折叠态展示行数，即「展开后还会多出几行」。more 行文案计数因此天然排除重复行，无需改文案。
- 超出部分全是重复行时 `hiddenCount` 为 0 → 不渲染 more 行，展开态强制归位为 `false`。
- `visibleTabs: 'all'`、去重预览态：行为不变。
- 会话卡片（§5.5）沿用原折叠：会话条目是快照数据、不是活动 tab，不参与重复判定。

### 边界情况

- **区块内几乎全是重复** → 折叠形同虚设，行数接近全量。这是**正确行为**：该区块本就应被看见并清理，不为此加阈值兜底。
- **展示行数超出用户设置的 `visibleTabs`** → 接受，不额外解释。曾考虑在 more 行补「N 个重复项已保持展开」，因扩大 i18n 面且信息价值低而推迟。

## 4. 实现

- `src/lib/fold.ts` `foldTabs` 新增可选第四参 `isExempt?: (item: T) => boolean`；不传时行为与既有实现完全一致（会话卡片依赖此点）。
- `src/components/WindowSection.tsx`、`src/components/DomainGroupList.tsx` 传入 `(tab) => dupCountByTabId.has(tab.id)`。两者已持有 `dupCountByTabId`，无新增 props。
- `src/manager/App.tsx` 无改动。

## 5. 验收标准

- [ ] limit=8、12 条中第 10/11 条为重复 → 折叠态展示 10 条（前 8 + 2 条重复），`hiddenCount` 为 2。
- [ ] 超限行全为重复 → `hiddenCount` 为 0，不渲染 more 行。
- [ ] 不传 `isExempt` 时折叠行为与修订前逐位一致。
- [ ] `visibleTabs: 'all'` 与去重预览态不受影响。
- [ ] hover 任一重复行时，同组成员在所有区块内均已渲染并高亮。
