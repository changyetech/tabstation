# 页面流程与逻辑性能优化

日期：2026-11-14。类型：Design spec（descriptive）。

## 目标与边界

保持真实标签页写穿操作、三种模式、全浏览器去重、稍后阅读的保存关闭/打开移除、会话模板式恢复、设置即时同步等既有目标。保持数据结构、权限、界面布局与正常路径的操作结果；仅优化内部计算并修复与既有语义冲突的异步时序。

不增加依赖，不实现虚拟列表、撤销栈、网络服务或大会话懒加载。

## 当前流程

- 图标/快捷键 → 后台读取设置与真实标签页 → 按作用域聚焦或创建管理页。
- 管理页 → `useTabs` 合流 Chrome 事件 → 排除自有页面和未知窗口 → 搜索、窗口/域名分组、全局重复组 → 激活、移动、拆窗、关闭等真实操作。
- 稍后阅读 → URL 去 hash 判重后持久化 → 关闭源标签；打开成功 → 移除对应已打开条目。
- 窗口会话 → 过滤自有页面与 chrome:// 的有序快照 → 持久化成功后按设置关闭源窗口；恢复时创建窗口、还原固定标签，保留会话。
- 设置页 → 合并默认字段 → 写入 storage → 管理页通过 onChanged 同步主题、语言及偏好。

## 方案取舍

采用局部等价算法优化与异步依赖排序。全面改造成全局状态库、虚拟列表或后台集中写入器会扩大本轮风险，且缺少实际渲染规模证据，暂不采用。现有 60ms 事件合流、30s 相对时间更新及关闭动效保留。

## 优化契约

1. 域名排序先为每个域名计算一次注册域/子域层级，再排序；保持私有后缀、多级后缀、数字排序、特殊组顺序及组内 tab 顺序。不在 URL 分组时二次解析 URL。
2. 域名分组与去重预览过滤分开记忆化；悬停重复行不应重新分组排序。域名总数仅随可见标签数据变化重算。
3. 批量稍后阅读用一次 URL 索引和一次清单复制，复杂度由逐条扫描/复制降到 O(原清单 + 批次)。保留首次条目的 id、URL、标题、图标与顺序；重复项仅更新 savedAt；输入不可变。
4. `useTabs` 对内容完全相同的快照复用旧数组，避免无变化事件引起派生计算；所有字段变化（含 mutedInfo）及顺序变化仍须传播，不新增永久缓存。
5. `useStorageState` 的初始旧读不得覆盖新状态。页面与后台的读改写统一通过 `updateKey`：按 storage key 使用 Web Locks 同源排他锁，锁内读取最新值、执行 updater、等待写入；打开标签页/窗口的等待在锁外。界面通过 onChanged 或成功返回值更新，不把未落盘值展示为已保存；订阅版本号阻止旧读/旧写完成回调覆盖新值。
6. 保存稍后阅读、批量保存及保存会话必须等待持久化成功才关闭源标签/窗口；失败保留源对象并反馈。打开稍后阅读必须等标签/窗口创建成功才移除，全部打开仅移除本批已打开的 id，保留等待期间新增条目。
7. 管理页 toast 定时器随卸载清理；其他经复现的缺陷在实施计划补充后修复。
8. 设置页等待写入成功再显示成功反馈；失败显示失败反馈，保留已保存状态，不回滚期间收到的更新。设置按最新持久化值合并 patch。
9. 会话重命名的 Enter/Escape 在输入法组合期间不执行提交/取消。
10. 移动菜单超高时限制为视口可用高度并内部滚动，定位夹在视口内；正常短菜单仍优先向下、空间不足向上。
11. 后台管理页查找/创建使用独立同源锁防止并发重复创建，并识别 pendingUrl。地址栏稍后阅读遵循后台打开 disposition；空查询不读取标签页/完整清单。
12. URL hostname 解析与可见 tab 过滤拆到轻量纯函数模块，后台不再因引用 grouping 模块而加载注册域后缀库；域名排序仍保留原库与精确规则。
13. 会话条目删除/移动在锁内校验操作时的条目快照；旧下标已过期则拒绝并反馈重试，避免并发删除后误操作其他条目。稍后阅读打开中的 id 防重入，失败或完成后释放。移动菜单先应用新限高再测量定位，覆盖视口增高场景。

Web Locks 同源页面/worker 排队与自动释放语义见 [Web Locks API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Locks_API)；pendingUrl 和 active 参数见 [Chrome Tabs API](https://developer.chrome.com/docs/extensions/reference/api/tabs)。SW 不持久缓存业务状态。

## 验收

- 改动前基线：38 个测试文件、279 个用例通过，生产构建成功。
- 对并发初始读取、存储失败/延迟、打开失败、打开期间新增清单项、相同及变更快照补回归测试。
- 以同一生成数据和同一 Node 环境比较优化前后域名分组及批量保存耗时；不设机器相关的耗时测试阈值。
- `make check` 与 `pnpm build` 通过；不以 jsdom 结果替代真实扩展 Chrome API 验收。

## 分析与实施结果

| 检查范围 | 结论与处理 |
| --- | --- |
| 后台入口、单例、地址栏 | 修复并发重复创建、pendingUrl 漏判、后台打开抢焦点、旧清单覆盖并发更新；空输入跳过 tabs 和完整清单读取，过期请求失败不清空新建议 |
| 标签页事件到列表 | 保留 60ms 首刷/尾刷合流、序号防旧快照与未知窗口过滤；相同完整快照复用数组，字段或顺序变化仍传播 |
| 全部模式、域名排序、搜索 | 注册域键预计算，URL 只解析一次；分组缓存独立于悬停/预览，域名统计不随搜索框输入重复计算；搜索范围和全局去重口径保留 |
| 窗口模式与真实标签操作 | 真实 index、当前窗口置顶、自有页面保护、固定标签约束保留；保存会话后关闭窗口改为等待持久化完成 |
| 稍后阅读、持久化同步 | 批量 upsert 改为线性索引；页面/后台共用锁内读改写；初始旧读不覆盖新事件；打开/保存失败保留源数据、显示双语失败反馈；删除失败恢复退场行；打开中的条目防重入，完成或失败后释放 |
| 会话卡片、拖拽、恢复 | 模板式恢复、固定标签还原、同/跨会话排序、删空会话规则保留；中文输入法组合期间不提前提交/取消重命名；锁内校验条目快照，拒绝过期下标防止误删/误移动 |
| 设置、主题、语言 | 设置按最新持久化值合并 patch，成功反馈等待写入，旧保存完成不覆盖新反馈；主题跟随系统和双语切换沿用现有实现 |
| 移动菜单 | 超高菜单按视口限高、内部滚动、位置夹边，移除默认 ul margin，保留短菜单向上/向下展开逻辑 |
| 动效与资源 | 保留已有单 rAF、400 粒子上限、600ms 错开上限、共享 AudioContext 与 reduced-motion；补充页面提示定时器清理 |
| 构建、权限、发布 | 提取 URL/可见 tab 工具，使后台不再加载 tldts；权限、版本来源、manifest、CI/发布流程保持现状 |

### 同数据性能对比

命令：`node scripts/performance.mjs --compare`，Node v24.15.0。基线提交：`0a7c9c03ba77d77eaaeaf78bf539edca73e62969`。以当前未提交改动对比 HEAD 源码，同一进程串行运行，预热 8 次、25 次中位数。脚本先断言新旧分组及批量保存结果等价，再测量；`--compare` 使用运行时 HEAD，提交后应选定原基线重新比较。无 `--compare` 则仅测当前代码。

| 场景 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 1,000 标签域名分组 | 12.596 ms | 4.167 ms |
| 5,000 标签域名分组 | 82.707 ms | 25.915 ms |
| 2,000 条清单 + 1,000 条批量保存（含 500 条重合） | 110.814 ms | 0.381 ms |
| 后台 JS 及静态传递依赖（未压缩） | 279,440 B | 20,745 B |
| 后台 JS 及静态传递依赖（逐文件 gzip 合计） | 117,834 B | 8,012 B |

体积统计从生产构建的 `dist/background.js` 递归遍历本地静态 import，读取文件实际字节；不把 manager chunk 的体积变化误报为扩展整体缩小。域名后缀库仍由管理页加载。算法微基准是本机测量，不代表浏览器端到端耗时或实际峰值内存。

### 验证边界与后续方向

最终验证：`make check` 通过（39 个测试文件、324 个用例，较基线新增 45 个）；`pnpm build` 与 `git diff --check` 通过。构建 manifest 版本为 0.3.0，与 package.json 一致，权限仍为 tabs / storage / favicon。独立复核发现的连续删除误删、重复打开及视口增高定位问题已补充失败复现、修复并验证。

现有分组、折叠、固定标签、去重、会话与动效测试继续作为回归约束；新增可控 Promise 的延迟/失败/并发用例。真实 Chrome 扩展环境下的 Web Locks 跨页与 worker 协调、窗口全屏与拖拽、滚动菜单视觉仍需手工验收，本轮自动化基于 jsdom/Chrome mock 与生产构建。

保留 ROADMAP 的行级渲染跳过和大会话懒恢复：前者需要稳定所有回调及移动菜单实时目标，后者涉及标签加载/丢弃时序，均不在本轮缺少端到端测量时贸然引入。地址栏非空查询目前仍全量扫描并排序，后续若大清单输入延迟实测显著，可独立优化 Top-K 选择。
